## 1. Current Routing & Telemetry Architecture

### Implemented Capabilities (Phase 3B Baseline)
- **`execution_telemetry` Table**: Persists each execution attempt in SQLite with `task_id`, `workflow_id`, `agent_id`, `executor_id`, `provider_id`, `model_id`, `duration_ms`, `success`, `retry_count`, `fallback_used`, `failure_class`, `cost_usd`, `input_tokens`, `output_tokens`, `quality_score`.
- **`ExecutorRouter` Scoring**: Basic empirical score:
  $$\text{Score} = w_{\text{cap}} \cdot S_{\text{cap}} + w_{\text{qual}} \cdot Q_{\text{emp}} + w_{\text{succ}} \cdot R_{\text{smoothed}} + w_{\text{rel}} \cdot 0.95 - P_{\text{cost}} - P_{\text{lat}}$$
  with Laplace Bayesian smoothing for cold start ($\alpha=4, \beta=1$).
- **`CircuitBreaker`**: Tracks failures per executor with a 300s cooldown.
- **Orchestrator Fallback**: Iterates through candidate chain generated by router.

### Limitations in Current Routing
1. **Decision Persistence Missing**: Router does not record *why* a candidate was selected versus rejected in a dedicated `routing_decisions` table.
2. **Global Rather Than Task-Specific Scores**: Empirical success is calculated across all tasks indiscriminately rather than segmented by `task_type` (e.g. `coding`, `documentation`, `security`, `repo_analysis`).
3. **No Recency Weighting**: An execution from 6 months ago currently carries the same mathematical weight as an execution from 5 minutes ago.
4. **Outcome Model Not Granular**: Quality score is binary ($1.0$ or $0.0$) rather than reflecting multi-factor engineering outcomes (`tests_passed`, `review_passed`, `security_passed`, `artifact_valid`, `human_approved`).
5. **No Routing Experiments or Stability Controls**: No structured mechanism to benchmark a challenger executor on sandbox/low-risk tasks or guard against routing oscillations.
6. **No Policy Version Tracking**: Routing weights and formula variations are not versioned (`routing_policy_version = "adaptive-v1"`).

## 4. Phase 3C Implementation Strategy

1. **Database Schema & Indexes**:
   - Add `routing_decisions` table with indexes on `task_id`, `workflow_id`, `executor_id`, `task_type`, `created_at`.
   - Add indexes on `execution_telemetry`.
2. **Adaptive Scoring Engine (`src/evoforge/model_router/adaptive.py` & `routing.py`)**:
   - Implement `AdaptiveRouter` with recency decay weighting (half-life parameter), task-type aggregation, and multi-dimensional outcome tracking.
   - Version policy as `adaptive-v1`.
3. **Execution Outcome Representation (`ExecutionOutcome`)**:
   - Track `tests_passed`, `review_passed`, `security_passed`, `artifact_valid`, `human_approved` in outcome telemetry.
4. **FastAPI Endpoints (`src/evoforge/api/server.py`)**:
   - Pydantic models for status, agents, executors, telemetry, routing decisions, events.
   - Replace all hardcoded mocks with real queries against `Database` and `EventStore`.
5. **Frontend Integration (`visual-brain/`)**:
   - Connect live feeds to real endpoints (`/api/status`, `/api/routing/recent`, `/api/telemetry/statistics`, `/api/events/recent`).
6. **CLI & Introspection**:
   - Implement `evoforge routing-stats`, `evoforge routing-history`, `evoforge executor-stats`.
7. **Comprehensive Testing & Verification**:
   - Unit and integration tests for adaptive routing, recency, task-type slicing, quality weighting, API endpoints, and zero mock data.
